# XMOS xCORE processor module for Ghidra

SLEIGH disassembler + p-code semantics for the XMOS xCORE architecture, written clean-room from
the XMOS architecture manuals (*The XMOS XS1 Architecture*, *xCORE-200: The XMOS XS2
Architecture (ISA)*, *xcore.ai / XS3 ISA*). Target: **Ghidra 12.1.4**.

| Language ID        | Architecture                         | Instructions (forms) |
|--------------------|--------------------------------------|----------------------|
| `xCORE:LE:32:XS1`  | XS1 (XS1-G/L/U, original XCore)      | 176 (209)            |
| `xCORE:LE:32:XS2`  | XS2 / xCORE-200 (dual issue)         | 195 (228)            |
| `xCORE:LE:32:XS3`  | XS3 / xcore.ai (FPU + 256-bit VPU)   | 250 (283)            |

ELF files with `e_machine` 203 (`EM_XCORE`) or 0xB49E (the older XMOS value) are opened as **XS3**
automatically. The ELF header can't tell XS2 from XS3: `e_flags` is 0 for both. XMOS images
record the architecture only in an `XMOS` note (`NT_ARCH` "XS2"/"XS3") in a `.xmosnote`
section, and the `.opinion` mechanism can only match `e_machine`/`e_flags`. This is harmless
for XS2, because XS3 decodes XS2 code identically: real xCORE-200 images give byte-for-byte
the same listing under both languages (see below). `ghidra_scripts/XcoreElfSetup.java` reports
the note and warns if it doesn't match the language. For XS1 firmware, pick the language by
hand. XS2 is not a superset of XS1: it re-encodes `TINIT*`, `TSETR`, `TSETMR`, `BYTEREV`,
`CLZ`, `BITREV`, `KRESTSP`, `KRET`, `DRET`, `DENTSP` and `DRESTSP`.

### Importing an XMOS `.xe`

An `.xe` is a container: an `XMOS` header followed by sectors, several of them ELF images
(small boot/loader images plus one application image per tile). Split it first, then import
the per-tile ELFs and run the setup script before analysis:

```
test/xe_extract.py app.xe out/       # out/app_n0_t0_1.elf = node 0, tile 0, application image
analyzeHeadless proj p -import out/app_n0_t0_1.elf \
    -scriptPath xCORE/ghidra_scripts -preScript XcoreElfSetup.java
```

`XcoreElfSetup.java` (in the GUI, Script Manager, category xCORE) does three things:

* It sets the dual-issue context from the XMOS mapping symbols. `$s.N` starts single-issue
  code and `$d.N` starts dual-issue code, like ARM's `$a`/`$t`.
* It sets cp/dp from the linker symbols `_cp`/`_dp`, so `ldw rX, cp[n]`, `BLACP` and
  dp-relative globals resolve.
* It checks the architecture note.

It also works after analysis: it re-disassembles code that was decoded in the wrong mode.

## Layout

```
data/languages/xcore_common.sinc     registers, pcodeop declarations (hand written)
data/languages/xcore_xs{1,2,3}.slaspec   GENERATED by scripts/gen_sleigh.py, do not edit
data/languages/xcore.ldefs / .pspec / .cspec / .opinion / .dwarf (DWARF register numbers)
ghidra_scripts/XcoreElfSetup.java    issue mode from $s/$d mapping symbols, cp/dp, arch note
scripts/isa_tables.py                encoding tables transcribed from the three manuals
scripts/gen_sleigh.py                operand packing, display syntax and semantics -> .slaspec
test/                                test suite (see below)
```

The encodings are irregular: there are 3r/2r/2rus packed operand fields (`27 + 9*a + 3*b + c`
style), `rus` vs `2r` sharing opcodes, `bitp` immediates, PFIX-prefixed long forms
(`lu6`/`lru6`/`lu10`) and the l2r/l3r/l4r/l5r/l6r/l2rus/l3rus/l4rus long formats. Because of
that, the specs are generated: every packed-operand combination becomes its own constructor
(about 3.2k/4.5k/5.1k constructors). **Edit `scripts/` and rerun `test/build.sh`. Don't edit
the `.slaspec` files.**

Dual issue (XS2/XS3): a context bit `dual` is set by `DUALENTSP` and cleared by `ENTSP` through
`globalset`. In linked images it is also pinned per range from the `$s`/`$d` mapping symbols
(`XcoreElfSetup.java`). In dual mode, pc-relative operands (`BRF*/BRB*`, `BLRF/BLRB`, `LDAP*`, `BRU`)
count in 4-byte units from the next bundle (`(inst_start+4) & ~3`). Bundles are decoded as two
sequential instructions. That's correct for data flow except where both lanes write the same
register, which the ISA forbids anyway.

Assembly syntax follows the XMOS assembler / LLVM XCore printer: `ldw r0, sp[0x1]`,
`set t[r6]:r11, r3`, `ldd r7, r6, r4[0x0]`, `chkct res[r0], 0x1` and so on.

## Semantics

* Real p-code covers integer ALU, shifts with the ISA's ≥32 behaviour, mul/div/rem, the long
  arithmetic ops (`LADD`, `LSUB`, `LMUL`, `MACCS`, `MACCU`, `LDIVU`, `LSATS`, `LEXTRACT`,
  `LINSERT`), `SEXT`/`ZEXT`/`MKMSK`, `BYTEREV`/`BITREV`/`CLZ`/`CLS`, and all loads and stores
  (word/half/byte, `LDD`/`STD`, sp/dp/cp-relative, `LDAW`/`LDAP`/`LDA16`).
* Control flow: branches (`BRFT/BRBT/BRFF/BRBF/BRFU/BRBU`, `BRU`), calls (`BL`, `BLRF/BLRB`,
  `BLA`, `BLACP`, `BLAT`), stack frames (`ENTSP`, `DUALENTSP`, `EXTSP`, `RETSP`, `KENTSP`,
  `KRESTSP`), returns (`RETSP`, `KRET`, `DRET`) and `BAU` (indirect jump). XS3 float ops (`FADD/FSUB/FMUL/FMACC/FEQ/FLT/FGT/FUN`) use the p-code float
  operators.
* The remaining 69 (XS1), 76 (XS2) and 116 (XS3) instructions are named pcodeops. These are
  resource, channel, port, timer, event and thread ops, kernel/debug calls, CRC/ZIP/UNZIP, and
  the VPU (`vR`/`vD`/`vC` 256-bit registers, `vSR` status). They still read and write the right
  GPRs and vector registers, and `WAITEU/WAITET/WAITEF` are modelled as computed jumps.
* `cspec` follows the XMOS ABI. Arguments go in r0–r3 then the stack from `sp[1]`. The return
  value is in r0, or r1:r0 for 64-bit values. r4–r10 are callee-saved; r11 and lr are scratch.
  cp and dp are preserved.

## Testing and coverage

```
export GHIDRA_INSTALL_DIR=/path/to/ghidra_12.1.4_PUBLIC
test/fetch_xmos.sh /tmp/xmos-ext            # optional: vendor objects + sources (pip, git)
XMOS_EXT=/tmp/xmos-ext test/run-tests.sh /tmp/xcore-tests
test/fetch-real-samples.sh /tmp/xmos-real && test/real-binaries.sh /tmp/xmos-real   # release binaries
```

(`run-tests.sh` symlinks the module into `$GHIDRA_INSTALL_DIR/Ghidra/Processors/xCORE` and
uses `../tools/ghidra-dis.sh`. The LLVM oracle loads `/usr/lib/llvm-21/lib/libLLVM.so` through
ctypes. No xcore assembler exists in LLVM, so `llvm-mc` cannot produce encodings.)

| Check | Result |
|---|---|
| XS1 vs LLVM 21 XCore disassembler, all 62,464 non-prefix 16-bit words | **99.92 %** (48 diffs, all explained) |
| XS1 vs LLVM, 1,020,896 32-bit items (every second halfword for 11 prefix values + 300k random) | **100.00 %** |
| XS2 / XS3 vs LLVM on the same corpus | 95.8 % / 95.2 % (16-bit), 99.5 % / 99.4 % (32-bit). Every diff is a documented XS2 re-encoding or an XS2/XS3-only instruction in space that XS1 leaves undefined |
| Every encoding form of `scripts/isa_tables.py` decodes (`test/enc_coverage.py`, 64 random fills per form) | 209/209 (XS1), 228/228 (XS2), 283/283 (XS3) |
| XS3 decoding of xcc-assembled `lib_nn` / `lib_tflite_micro` `.S` objects vs their sources (mnemonic, registers, literal immediates, dual-issue bundles) | **621/621 instruction groups (100 %)**, 18 functions, including VPU (`vldr/vstr/vlmacc/vlsat/vladd/vlashr/vlmul/vdepth*/vsetc/vldc/vldd/vstd/vstrpv/vclrdr/vsign/vstc`), FPU and XS2 ops |
| ELF import (opinion → XS3) + auto-analysis + decompile of all 76 vendor-built C and assembly objects linked by `test/xobj2elf.py` | 228 functions, 14,078 instructions, 0 error bookmarks, 0 decompile failures, 0 bad-instruction warnings |

The 48 explained 16-bit diffs are `CHKCTI` with immediates 0/9/10/11. LLVM prints these as
bitp values (32/16/24/32). The manual says the operand is a plain `us` (0…11), which is what
this module prints.

## Real-world binaries

These are public XMOS release builds, compiled and linked by xcc, under the XMOS Public
Licence v1. They are not committed here: `test/fetch-real-samples.sh` downloads them with
pinned tags and checks their SHA-256.

* `sw_usb_audio` v8.1.0: `app_usb_aud_xk_216_mc` (xCORE-200, **XS2**) and
  `app_usb_aud_xk_316_mc` (xcore.ai, **XS3**), configuration `1AMi2o2xxxxxx`. The release
  also supplies the `lib_xud` assembly sources.
* `sln_voice` v0.20.0: `example_ffd.xe` and `example_audio_mux.xe`. `sln_voice` v0.10.0:
  `application_ffd.xe`. All three are XS3 (FreeRTOS, lib_xs3_math, VPU code).

```
test/fetch-real-samples.sh /tmp/xmos-real
GHIDRA_INSTALL_DIR=... test/real-binaries.sh /tmp/xmos-real /tmp/xcore-real   # ~30 min, JOBS=3
```

The script splits each `.xe` into its 4 tile ELFs (20 images in total). For each image it
imports with no `-processor` and runs `XcoreElfSetup.java` as a pre-script. It then
auto-analyses, decompiles every function and compares every decoded instruction with LLVM 21
at the same address. The results:

| Check (20 tile images) | Result |
|---|---|
| ELF opinion | `xCORE:LE:32:XS3` for all of them. The 8 XS2 images give the **same listing** under `xCORE:LE:32:XS2` (0 differing lines) |
| Auto-analysis | 4,368 functions, 188,905 instructions. **0** bad-instruction bookmarks and **0** instructions in non-executable memory |
| Decompile | 4,341 functions (lib_xud's `PidJumpTable` data, typed `STT_FUNC`, is skipped). **4 failures** (see known gaps), 0 timeouts, 0 `halt_baddata` |
| vs LLVM XCore (XS1 ISA) | 159,816 identical. The other 29,089 are XS2/XS3-only opcodes (`nop`, `ldd`/`std`, `dualentsp`, VPU/FPU ops, `crc32_inc`...) or the documented XS2 re-encodings. **0 unexplained** |
| Pc-relative targets | All 22,471 `bl`/`bt`/`bf`/`bu` targets, single- and dual-issue, land on a decoded instruction or an ELF `FUNC` symbol |
| Issue mode vs `$s`/`$d` mapping symbols | 0 pc-relative instructions decoded in the wrong mode |
| lib_xud sources vs decoding (`test/linked_srccheck.py`) | XS2: 495/495 instruction groups. XS3: 530/530 (dual-issue bundles, `crc32_inc`, `crcn`, `crc8`, `outpw`/`inpw`) |

The lib_xud check matters most. 66 (XS2) and 67 (XS3) branch, call and `ldap` operands name a
label in the source. The linked image resolves each of them to an address, and each matches
the target Ghidra computes. For example, the single-issue `bf r0, Return` in
`UsbTestModeHandler_asm` and the dual-issue `bu Return` in `ResetIntHandler` both resolve to
the `Return` symbol. This checks the dual-issue pc-relative rule (`((pc + 4) & ~3) + 4*imm`)
against the vendor assembler and linker, which the relocatable objects could not do.

### Found and fixed

* **Dual-issue code reached indirectly was decoded in the wrong mode.** lib_xud event vectors
  and its `PidJumpTable` targets were decoded as single issue. On the xk_316 image a plain
  import had 4 conflicting-instruction bookmarks and 25 pc-relative instructions in the wrong
  mode. XMOS ELFs mark issue mode with `$s.N`/`$d.N` mapping symbols, and
  `XcoreElfSetup.java` now applies them, which brings both counts to 0. Compiled functions are
  not affected: 97 % of the `FUNC` symbols start with `ENTSP` or `DUALENTSP` in their first
  bundle, even `dualentsp 0` leaves. The exceptions are runtime assembly: the
  `memcpy`/`memset` trampolines, `_SetupThread` and the RTOS IRQ handler.
* **`VFTFF` / `VFTTF` (0x2fec / 0x2fed) didn't decode.** The `BRU` constructor was split on
  the `dual` context and shadowed them. The split now lives in sub-tables. This was 1 bad
  instruction in each sln_voice tile-1 image (lib_xs3_math FFT). `test/enc_coverage.py`, now
  part of `run-tests.sh`, checks that every encoding in the ISA tables decodes. The LLVM
  comparison can't catch this, because "both undefined" counts as agreement.
* **`CRCN` and `CRC32_INC` operand order and roles.** The lib_xud sources are
  `crcn crc, data, poly, n` and `crc32_inc crc, data, poly, idx, bitp`. The module was
  following the manual's operand numbering, which is wrong for these two.
* **No DWARF register mapping.** Ghidra's DWARF importer hit a NullPointerException on every
  function (109 errors per image). `xcore.dwarf` now maps r0–r11=0–11, cp=12, dp=13,
  sp=14 (CFA) and lr=15, which match xcc's `.debug_frame`.
* cp/dp: `XcoreElfSetup.java` (and `test/SetCpDp.java`) now take them from `_cp`/`_dp`.

## Known gaps / untested

* Dual-issue pc-relative scaling is now checked against linked xcc output (see Real-world
  binaries) for `bt`/`bf`/`bu`/`bl`/`ldap`. `BRU` (relative jump by register, used for switch
  tables) follows the same rule, but no source-level check covers it.
* Most XS2/XS3-only instructions that are missing from the vendor sources are checked only
  against the manual encoding tables. That includes `XOR4`, `LINSERT`,
  `ELATE`, `DVLD`/`DVST`, `FMAKE`, `FSPEC`, `VLADSB`, `VCM*`, `VFT*`, `VDEPTH16`,
  `VLMACCR1`, `FLUSH`, `INVALIDATE` and the kernel/debug ops.
* **Stripped images (no `$s`/`$d` symbols).** Issue mode then comes only from
  `DUALENTSP`/`ENTSP` flow. Compiled code is decoded correctly. Hand-written dual-issue
  assembly that is entered through a pointer is not: on the xk_316 image with its mapping
  symbols renamed, 25 pc-relative instructions are decoded in the wrong mode.
  `XcoreElfSetup.java` run as a post-script falls back to two heuristics, and on that image
  they only bring it down to 22, because the wrongly decoded lib_xud code branches into
  itself. The heuristics are: LDAP targets inherit the LDAP's mode, and unreferenced code
  heads inherit the mode of the code before them. Fix the rest by setting the `dual` context
  register by hand.
* Code reached from callers in both modes keeps the mode of the first flow that reaches it.
  This only affects the entry bundle before `DUALENTSP`/`ENTSP` and mode-agnostic stubs, so it
  is harmless.
* Decompiler: 2 lib_xs3_math functions (`DSPTR_022054`, `DSPTR_021003`, in both FFD
  builds) fail with "Trying to construct memory range beyond end of address space". The code
  stores a `mkmsk r0, 32` sentinel (-1), reloads it on a path that dereferences it, and the
  decompiler then sees a 4-byte load at 0xffffffff. Replacing those instructions with nops lets
  them decompile, so this is a decompiler limitation, not wrong p-code.
* Ghidra's DWARF line-table import reports `IllegalArgumentException for source map entry
  ... -123` for some lines of xcc's DWARF (line 133 shows up as -123). These are only Error
  bookmarks of type DWARF and don't affect code. DWARF-typed `void f(void)` functions also get
  the generic "Unknown calling convention -- yet parameter storage is locked" decompiler
  warning.
* The ELF loader has no relocation handler for the XMOS relocation types. Unlinked `.o`/`.obj`
  files also put their code in `SHT_LOOS` fragments with `sh_addr`=1, which Ghidra loads at odd
  addresses. Import linked `.xe` tile images (`test/xe_extract.py`), or use `test/xobj2elf.py`
  to link objects first. cp and dp aren't known to analysis unless set (`XcoreElfSetup.java`).
* VPU, resource, channel and port semantics are opaque pcodeops. The decompiler shows them as
  calls such as `vlmacc(...)`.
